# База данных

## Что есть сейчас

`database/schema.sql` — SQL-схема для SQLite/Cloudflare D1.
`lib/db/schema.ts` — ее описание для Drizzle ORM.

Это **исходный код схемы**, а не развернутая БД. На опубликованном стенде
binding `DB` отсутствует, поэтому:

- товары и состояние демо-админки хранятся только в `localStorage` браузера;
- email OTP API возвращает `503`, пока не подключены `DB` и
  `OTP_CODE_PEPPER`; реальных аккаунтов на стенде нет;
- оформленная заявка визуально подтверждается, но не сохраняется на сервере;
- API 1С проверяет JSON и отвечает `202 validation-only`;
- реальных пользовательских данных в D1 сейчас нет.

## Таблицы

| Таблица | Содержимое |
| --- | --- |
| `store_settings` | настройки магазина, включая стартовую ёмкость каталога 100 позиций |
| `users` | покупатели, менеджеры и администраторы |
| `sessions` | серверные сессии |
| `otp_challenges` | HMAC-хеши одноразовых кодов, лимиты попыток и срок действия |
| `consents` | отдельные согласия, версия документа и отзыв |
| `products` | карточки шин и дисков, включая `external_id` из 1С |
| `product_images` | URL и порядок фотографий |
| `inventories` | остатки по складам |
| `prices` | цены по типам |
| `fitments` | применяемость к маркам/моделям авто |
| `orders` | шапка заказа и отметка выгрузки в 1С |
| `order_items` | состав и зафиксированная цена заказа |
| `sync_runs` | идемпотентность и аудит обменов |
| `admin_audit_log` | журнал действий администраторов |

### Подготовленные 100 товарных позиций

В `store_settings` записано значение `catalog_initial_capacity = 100`, а
админка показывает занятые и свободные позиции. Пустые строки товаров не
создаются: в реляционной БД резервировать их заранее не требуется. Таблица
`products` уже рассчитана на 100 и больше реальных карточек, а фотографии,
остатки, цены и применяемость хранятся в связанных таблицах.

## Production для РФ

Для реального магазина основной БД должна стать PostgreSQL, физически
размещенная в Российской Федерации. Местонахождение нужно подтвердить договором
и документами провайдера, а не только названием региона в панели.

До сбора данных необходимо:

1. получить реквизиты ИП и определить оператора персональных данных;
2. выбрать российского хостинг-провайдера и регион;
3. создать отдельные development, staging и production базы;
4. перенести SQLite-схему в PostgreSQL-миграции;
5. зашифровать соединение, ограничить сеть и завести отдельного пользователя
   БД с минимальными правами;
6. настроить резервные копии и проверить восстановление;
7. определить сроки хранения для каждой цели;
8. оформить необходимые уведомления Роскомнадзора до начала обработки.

## Миграция схемы на PostgreSQL

Основные изменения:

- `TEXT`-даты заменить на `timestamptz`;
- булевы `INTEGER` заменить на `boolean`;
- UUID генерировать сервером приложения или PostgreSQL;
- добавить `numeric` только где действительно нужны дробные величины; деньги
  оставить `bigint` в копейках;
- ограничения ролей и статусов оформить PostgreSQL enum или `CHECK`;
- перенести подготовленные `consents` и `admin_audit_log`, сохранив индексы;
- для импорта 1С использовать транзакции и staging-таблицы при больших объемах.

Cloudflare D1 можно оставить для обезличенного каталога как кэш, но не как
первичную базу российских персональных данных.
