# Результаты локальных испытаний

Дата: 5 сентября 2026. Windows x64, PostgreSQL 18.4, Node.js, отдельная временная
база apex_perf_*. 50 000 товаров импортированы настоящим CSV importer; по 25 000
шин и дисков, 20 тестовых брендов, 200 моделей, типизированные параметры,
часть товаров неактивна/без остатка. Данные явно TEST ONLY и не публиковались.

Набор намеренно повторяет размеры и даёт широкую выборку. Это не копия реального
ассортимента. Один прогон, без моделирования WAN, конкурентных покупателей,
дискового пространства российского VDS и browser E2E. Значения ниже — wall time
вызовов сервисов, не p95/p99 и не EXPLAIN ANALYZE.

| Сценарий | Время |
| --- | ---: |
| Потоковый импорт 50 000 новых строк | 516 481 мс (8,6 мин) |
| Повторный импорт 100 строк | 1 161 мс |
| Фильтр шин + stock + сортировка цены + фасеты | 746 мс |
| Фильтр дисков + фасеты | 392 мс |
| Глубокая страница с price_desc | 422 мс |
| Поиск SKU + фасеты | 457 мс |
| Товар по slug | 4,8 мс |
| Автомобиль → шины | 304 мс |
| Автомобиль → диски | 361 мс |
| Guest checkout | 72 мс |

Проверены assertions: 24 записи в странице, правильный тип/размер, сортировка,
неактивный/нулевой остаток, отсутствие дубликатов после повтора, проверенная
применяемость, неизвестный автомобиль, гостевая корзина, конкурентный merge,
серверная сумма, снимок характеристик и идемпотентность заказа.

После этого добавлено хранение резервов с TTL. Дополнительный прогон на 100 SKU
подтвердил все 6 миграций, сохранение локальных резервов при импорте остатков,
cleanup без повторного освобождения, отказ отгрузки истёкшего резерва и отмену.
Финальный повтор на 100 SKU также проверил частичный CSV с отрицательной ценой
и повтором SKU: одна корректная строка обновлена, две ошибки сохранены в БД.
Числа большого прогона относятся к версии до добавления двух блокировок в
импорте остатков; после финальных изменений throughput 50 000 повторно не измерялся.

Узкие места: importer выполняет несколько запросов на строку и относительно
медленный; каталог вычисляет точное COUNT и фасеты; глубокий OFFSET растёт с
размером выборки. Следующие измерения на staging: EXPLAIN (ANALYZE, BUFFERS),
p95 под параллельными запросами, 100 000/300 000 SKU, realistic распределение
размеров/складов, browser smoke, долгий импорт после рестарта, backup/restore.
300 000 SKU — архитектурная цель, не подтверждённый нагрузочный результат.

## Воспроизведение

Создать ПУСТУЮ изолированную PostgreSQL-базу с префиксом apex_perf_. Задать
PERFORMANCE_DATABASE_URL (только secret окружения), PERFORMANCE_PRODUCT_COUNT
(default 50000) и выполнить `pnpm perf:catalog`. Скрипт отказывается запускаться
в NODE_ENV=production и в базе с существующей products. Он применяет миграции,
импортирует поток, запускает запросы/assertions и печатает измерения.
Скрипт не удаляет БД: она остаётся для ручного анализа. Не запускать на рабочей БД.
