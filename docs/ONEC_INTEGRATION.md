# Подключение реальной 1С

## Что уже реализовано

Сайт содержит версионированный JSON API:

- `GET /api/1c/health`;
- `POST /api/1c/import/products`;
- `POST /api/1c/import/stock-prices`;
- `POST /api/1c/import/fitments`;
- `GET /api/1c/orders/export`;
- `POST /api/1c/orders/acknowledge`.

Есть проверка структур через Zod, общий токен, ограничение размера запроса,
разбиение больших SQL-пакетов, идемпотентный `syncId`, экспорт состава заказа и
подтверждение получения заказа.

Пока секрет и БД не подключены, это режим проверки контракта, а не рабочий
обмен.

## Предпочтительный вариант

Для 1С:УНФ, 1С:Управление торговлей или 1С:ERP разработать расширение
конфигурации либо внешнюю обработку. Она использует штатные HTTP-клиенты
платформы, формирует JSON и запускается регламентным заданием. Изменять типовую
конфигурацию напрямую не нужно: это усложняет обновления.

Если в организации уже используется CommerceML, можно написать адаптер
CommerceML → внутренний JSON API. Текущий контракт проще для остатков,
нескольких складов, статусов и явного подтверждения заказов.

## Последовательность обмена

### Из 1С на сайт

1. Первичная полная выгрузка номенклатуры.
2. Выгрузка цен и остатков после успешной загрузки товаров.
3. Выгрузка применяемости по марке, модели, году и поколению.
4. Далее — изменения каждые 5–15 минут или по событию записи.
5. Фото передаются отдельными файлами в объектное хранилище; API товара получает
   URL после успешной загрузки.

### С сайта в 1С

1. 1С каждые 1–2 минуты вызывает `GET /orders/export`.
2. Для каждого заказа ищет документ по `siteOrderId`.
3. Если документа нет — создает заказ клиента и строки товаров.
4. Записывает документ и фиксирует транзакцию.
5. Только после успешной записи вызывает `POST /orders/acknowledge`.
6. При сетевой ошибке повторяет запрос с тем же `syncId`.

конфигурации и версии 1С.

## Обязательное сопоставление

Перед разработкой обработки согласовать:

| Сайт | 1С |
| --- | --- |
| `externalId` | `УникальныйИдентификатор()` ссылки номенклатуры либо стабильный внешний код |
| `sku` | артикул |
| `kind` | вид/группа номенклатуры: шина или диск |
| размеры шин | свойства номенклатуры width/profile/diameter |
| параметры дисков | PCD, ET, DIA, диаметр |
| `warehouseCode` | стабильный код склада |
| retail price | выбранный вид цены |
| `make`, `model`, `generation`, годы | регистр сведений или лицензированный каталог применяемости |
| `siteOrderId` | дополнительный реквизит заказа клиента |
| статусы сайта | статусы/состояния заказа в конкретной конфигурации |

Нельзя использовать меняющееся наименование как ключ. Ключ — GUID или
стабильный внешний код.

## Безопасность

1. API обмена размещается в российском backend-контуре.
2. Используется HTTPS и случайный секрет не короче 32 байт.
3. Секрет хранится в защищенном хранилище 1С и secret manager сервера.
4. Желательны IP allowlist, VPN или mTLS.
5. Полные тела с персональными данными не записываются в обычные логи.
6. Доступ к запуску и просмотру журнала обмена ограничивается ролями.
7. Токен регулярно ротируется.

## Надежность

- каждый пакет имеет уникальный `syncId`;
- повтор завершенного пакета не меняет данные;
- число и результат записей фиксируются в `sync_runs`;
- сначала номенклатура, затем остатки/цены;
- заказ подтверждается только после записи в 1С;
- ошибки 429/5xx повторяются с экспоненциальной задержкой;
- 4xx, кроме 429, требуют исправления данных и не повторяются бесконечно;
- nightly-задача сверяет контрольное количество товаров и остатки.

## Что нужно от владельца 1С

Для завершения интеграции нужны:

1. название конфигурации, версия платформы и режим (файловый/серверный/облако);
2. копия или отдельная тестовая база;
3. список организаций, складов и видов цен;
4. правила резервирования и отображения доступного остатка;
5. примеры карточек шины и диска с заполненными свойствами;
6. требуемый тип документа заказа и схема статусов;
7. способ хранения фото;
8. технический пользователь 1С и согласованный сетевой доступ.

После этого 1С-разработчик делает расширение, проводит первичную выгрузку в
staging, сравнивает контрольные товары и только затем включает расписание в
production.
