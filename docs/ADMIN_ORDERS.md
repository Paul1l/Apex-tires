# Заказы в админке

Раздел для сотрудников с ролями `manager` и `admin`. Доступ — только после
входа сотрудника в `/admin` (`docs/AUTHENTICATION.md`); страницы проверяют
сессию через `getStaffPageAccess`, API — через `requireUserRole` (там же
проверка Origin для изменений). Без доступа страницы `/admin/orders/**`
переадресуют на `/admin`.

## Где работать

| Адрес | Что там |
| --- | --- |
| `/admin` → «Заказы» | список заказов внутри панели управления |
| `/admin/orders` | тот же список отдельной страницей; фильтры сохраняются в адресе |
| `/admin/orders/{id}` | карточка заказа: всё о заказе и действия с ним |

Номер заказа в списке — ссылка на карточку. Ссылка несёт текущие фильтры,
поэтому «Назад к заказам» возвращает к тому же списку и странице. На странице
списка слева одна ссылка «Панель управления»; в карточке — «Назад к заказам»
слева и «Панель управления» справа.

## Список заказов

- **Поиск** — одна строка: номер заказа, имя покупателя, email (часть строки,
  без учёта регистра) и телефон. Телефон можно вводить в любом виде:
  `8 913 123-45-67`, `+7 (913) 123 45 67` или часть цифр (от трёх). Символы
  `%` и `_` ищутся как обычные символы.
- **Фильтры** — статус заказа, состояние передачи в 1С, даты «с» и «по».
  Даты — календарные дни **по времени Барнаула** (Asia/Barnaul), обе границы
  включительно: заказ в 23:59 по Барнаулу попадает в этот день, даже если по
  UTC это уже другой день. Всё время в разделе показано по Барнаулу.
- **Страницы** — по 25 заказов, новые сверху; общее количество найденных
  заказов показано под таблицей.
- **Быстрая смена статуса** — выпадающий список в строке. Отмена заказа
  требует подтверждения. Комментарий к смене статуса пишется в карточке.

## Карточка заказа

- состав: товар, артикул, количество, цена и сумма строки на момент заказа;
  ссылка «Открыть на витрине», если товар активен;
- итоги: товары, скидка, доставка, итого;
- покупатель: имя, телефон, email, оформлен ли заказ из личного кабинета;
- получение: способ, адрес, шиномонтаж, комментарий покупателя, состояние
  резерва;
- история статусов: статус, время, кто изменил и комментарий;
- передача в 1С: состояние, число неудачных попыток, время последней попытки
  и передачи, следующая попытка, номер в 1С, безопасный текст ошибки;
- комментарии сотрудников;
- действия: смена статуса с комментарием, статус оплаты, комментарий
  сотрудника, повтор неудачных отправок в 1С.

Результат каждого действия выводится под формой и озвучивается экранным
диктором (`aria-live`); ошибки — с ролью `alert`.

## Статусы и их последствия

| Статус | Значение | Что происходит с остатком |
| --- | --- | --- |
| `new` — Новый | заказ оформлен | товар зарезервирован при оформлении |
| `confirmed` — Подтверждён | наличие проверено | — |
| `processing` — В работе | комплектуется | — |
| `ready_for_pickup` — Готов к выдаче | ждёт покупателя | — |
| `shipped` — Отправлен | передан покупателю или в доставку | резерв списывается со склада |
| `completed` — Завершён | заказ выполнен | резерв списывается со склада (если ещё не списан) |
| `cancelled` — Отменён | заказ отменён | резерв снимается, товар возвращается в продажу |

Правила переходов — прежние, T21c их не менял (триггеры миграций 005 и 006):

- между статусами можно переходить в любом направлении;
- если резерв истёк, можно только вернуть заказ в «Новый» или отменить его
  (`409 ORDER_RESERVATION_EXPIRED`); менеджер проверяет наличие и оформляет
  новый заказ, старый отменяет;
- повтор текущего статуса ничего не меняет (см. ниже) и ничего не списывает
  дважды;
- возврат отменённого заказа в работу **не восстанавливает резерв**: карточка
  предупреждает об этом, наличие нужно проверить вручную.

Комментарий к смене статуса необязателен, до 2000 символов. Он сохраняется в
истории статусов вместе с именем сотрудника. В истории строка без сотрудника
означает оформление заказа, обмен с 1С или системное действие.

Запрос с текущим статусом заказа (например, из устаревшего списка или после
двойного нажатия):

- **без комментария** — ничего не меняется: ни заказ, ни история статусов, ни
  журнал действий, уведомление не ставится. Ответ `200` с `unchanged: true`
  (`status` и `previousStatus` равны текущему статусу). Исключение — другой
  `paymentStatus` от администратора: он сохраняется и пишется в журнал как
  `order.payment_status_updated`, ответ с `unchanged: false`;
- **с комментарием** — отклоняется (`409 ORDER_STATUS_UNCHANGED`), чтобы текст
  не потерялся: для этого есть комментарии сотрудников.

1С может прислать свой статус и статус оплаты через
`POST /api/integrations/1c/v1/order-statuses/batch`; он записывается поверх
статуса из админки и попадает в историю без сотрудника.

## Статус оплаты

Допустимые значения — те же, что уже принимают API админки и обмен с 1С:

| Значение | Подпись |
| --- | --- |
| `pending` | Ожидает оплаты (по умолчанию для нового заказа) |
| `paid` | Оплачен |
| `failed` | Ошибка оплаты |
| `refunded` | Возврат оплаты |

Менять статус оплаты может **только роль `admin`** (`PATCH
/api/admin/orders/{id}/payment`); менеджер видит его только для чтения. Поле
`paymentStatus` в запросе смены статуса заказа тоже принимается только от
администратора, от менеджера — `403 PAYMENT_STATUS_FORBIDDEN`.

## Комментарии сотрудников — внутренние

Комментарии хранятся в таблице `order_comments` (автор, текст 1–2000 символов,
время) и показываются только в админке. Их не читает ни один API покупателя,
они не попадают в письма покупателю и в журнал действий (там — только длина).
Удаления и правки комментариев нет: это журнал работы с заказом. Не пишите в
комментарии лишние персональные данные.

## Уведомление покупателя

Письмо покупателю о смене статуса ставится **только в очередь
`notification_outbox`** в той же транзакции, что и смена статуса; отправляет
его фоновое задание уведомлений. HTTP-запрос админки ничего не отправляет.
Письмо ставится в очередь, если у заказа есть email и новый статус —
«Подтверждён», «Готов к выдаче», «Отправлен» или «Отменён». В письме только
номер заказа и статус, комментарии сотрудников в него не попадают.

Сейчас постановка выключена (`CUSTOMER_STATUS_NOTIFICATIONS_ENABLED = false` в
`server/services/admin-order-factory.ts`): провайдер писем ещё не знает шаблон
`customer-order-status-changed`, и такие письма падали бы и повторялись.
Чтобы включить: добавить шаблон в
`server/integrations/notifications/yandex-postbox-notification-provider.ts`
(текст готов — `renderCustomerOrderStatusNotification` в
`server/services/admin-order-notifications.ts`) и поставить флаг в `true`.

## Передача в 1С

Карточка показывает состояние передачи заказа (`pending`, `processing`,
`synced`, `failed`). При ошибке доступна кнопка «Повторить неудачные отправки»
— тот же запрос, что в разделе «Обмен с 1С» (`POST
/api/admin/integrations/1c/retry`). Она возвращает в очередь **все** заказы с
ошибкой передачи, не только открытый. Текст ошибки показывается в безопасном
виде: email и телефоны скрыты, длина ограничена.

## Журнал действий

Каждое изменение пишется в `admin_audit_log` (сотрудник, время, заказ):

| action | details |
| --- | --- |
| `order.status_updated` | прежний и новый статус (только при реальной смене), оплата (если менялась), был ли комментарий |
| `order.payment_status_updated` | прежний и новый статус оплаты |
| `order.comment_added` | id комментария и его длина |

## API

| Метод и путь | Роли | Назначение |
| --- | --- | --- |
| `GET /api/admin/orders` | manager, admin | список: `q`, `status`, `integrationStatus`, `from`, `to` (ГГГГ-ММ-ДД), `page`, `pageSize` (1–100, по умолчанию 25); ответ `{ ok, items, pagination: { page, pageSize, total, totalPages } }` |
| `GET /api/admin/orders/{id}` | manager, admin | карточка заказа, `permissions.canChangePaymentStatus` |
| `PATCH /api/admin/orders/{id}/status` | manager, admin | `{ status, comment?, paymentStatus? }`; `paymentStatus` — только admin; ответ `{ ok, status, previousStatus, notificationQueued, unchanged }` |
| `PATCH /api/admin/orders/{id}/payment` | admin | `{ paymentStatus }` |
| `POST /api/admin/orders/{id}/comments` | manager, admin | `{ body }`, ответ `201 { ok, comment }` |

Ответы с данными заказа — с `Cache-Control: no-store`. Тело запросов —
только `application/json` (иначе `415`) и только JSON-объект: `null`, массив
или строка дают `422 VALIDATION_ERROR` с русским сообщением («Выберите
допустимый статус заказа.», «Выберите допустимый статус оплаты.», «Введите
текст комментария.»). Ошибки: `401` без входа, `403` без
прав или со стороннего сайта, `404 ORDER_NOT_FOUND`, `409` (истёк резерв,
статус не изменился), `422 VALIDATION_ERROR` / `INVALID_ORDER_ID`, `503`
без PostgreSQL (`ORDER_STORAGE_NOT_CONFIGURED`) или при его недоступности
(`DATABASE_UNAVAILABLE`).

## Миграция 012

`012_order_administration.sql` только добавляет объекты и заменяет одну
функцию триггера:

- таблица `order_comments` (`order_id` с `ON DELETE CASCADE`,
  `author_user_id` с `ON DELETE SET NULL`, текст 1–2000 символов);
- индексы `orders(created_at DESC)` и `orders(status, created_at DESC)` для
  списка. Замер на 50 000 заказов (PostgreSQL 16): первая страница без
  фильтров — 0,2 мс, фильтр по дню — 0,4 мс, фильтр по редкому статусу —
  0,6 мс (без индекса по статусу — 1,6 мс). Поиск по подстроке читает таблицу
  целиком (~0,1 с на 50 000 заказов); если заказов станет на порядок больше,
  следующий шаг — GIN-индексы `pg_trgm` по имени, email и номеру после
  `EXPLAIN` на реальной базе;
- `record_order_status_history()` записывает в историю ещё и сотрудника и
  комментарий. Сервис админки задаёт их через `set_config(..., true)` —
  только на время своей транзакции — прямо перед `UPDATE` и очищает сразу
  после. Оформление заказа, обмен с 1С и задание резервов эти значения не
  задают, их строки истории остаются без сотрудника, как раньше.

Роль приложения получает права на новую таблицу через права по умолчанию
(`deploy/postgres/init/10-app-role.sql`); проверено применением 012 после
скрипта роли.
