# Настройки магазина в админке

Данные магазина, которые видят покупатели, меняются в админке без
пересборки сайта: Админка → «Настройки» (`/admin?section=settings`).
Реквизиты продавца, бренд, город и режимы каталога по-прежнему задаются в
переменных окружения сервера (см. ниже).

## Что можно изменить

| Группа | Поля | Где используется |
|---|---|---|
| Контакты | основной телефон; до 5 дополнительных; email магазина; email для обращений и уведомлений; WhatsApp, Telegram, ВКонтакте (только `https://`) | основной телефон, email, WhatsApp, Telegram — шапка и подвал, страница контактов, документы, микроразметка; ВКонтакте — только микроразметка (`sameAs`); дополнительные телефоны сейчас нигде не показываются (показ — изменение дизайна, решение заказчика); **email для обращений** — получатель писем сотрудникам о новых заказах и заявках на подбор (если пуст — email магазина) |
| Адрес и карта | адрес; широта и долгота (через точку, можно оставить обе пустыми); ссылка на карточку 2ГИС (обязательна, `https://`) | страница контактов, документы, микроразметка (`GeoCoordinates`) |
| Часы работы | одна строка, как увидят покупатели | шапка, контакты, микроразметка |
| Доставка | самовывоз, доставка по городу, доставка в другие города: включено/выключено и условия (до 1000 символов) | форма заказа, документы; **сервер отклоняет заказ с выключенным способом** |
| Услуги | шиномонтаж, балансировка, установка колёс, сезонное хранение, до 10 других услуг | шиномонтаж — пункт меню, блок услуг и галочка в форме заказа; **шиномонтаж к заказу сервер принимает, только если он включён**; балансировка, установка, хранение и другие услуги сохраняются, но на витрине пока не показываются (показ — изменение дизайна, решение заказчика) |

Пустое поле означает «не показывать» (в базе — `null`). Проверка — та же
схема, что у сервера (`server/validators/site-settings-schema.ts`): телефоны
из цифр, пробелов, скобок и дефисов; корректный email; ссылки только
`https://` (ссылки `javascript:`, `data:` и `http:` отклоняются); длина
текстов ограничена. Ошибка показывается у конкретного поля.

Стоимость доставки здесь не задаётся: она хранится в `store_settings`
(`delivery_<способ>_price_kopecks`) как раньше.

## Кто может менять

- **Администратор** (`admin`, вход по коду из приложения-аутентификатора) —
  просмотр и сохранение.
- **Менеджер** (`manager`) — только просмотр, с пометкой, что менять может
  администратор.
- Покупатели и сотрудники, вошедшие по коду из письма (сессия покупателя), —
  нет доступа (`403`).

Сохранение проверяет источник запроса (Origin) — как все изменения в
админке. Каждое сохранение с изменениями пишется в `admin_audit_log`:
действие `settings.site_updated`, `entity_type = store_settings`, в
`details` — ключ, **список изменённых групп** (`contacts`, `location`,
`workingHours`, `delivery`, `services`) и откуда были прежние значения
(`database`, `defaults`, `invalid`). Сами значения (телефоны, email) в журнал
не пишутся.

**Одновременные правки.** Форма помнит версию настроек
(`store_settings.updated_at`). Если другой администратор сохранил настройки
после открытия формы, сохранение отклоняется (`409
SITE_SETTINGS_VERSION_CONFLICT`), форма предлагает «Загрузить актуальные
данные». Несохранённые изменения отмечены в нижней панели; при закрытии
вкладки браузер предупредит о них.

## Что остаётся в переменных окружения и почему

Блок «Задаётся на сервере» в том же разделе показывает основные из этих
значений (только чтение) и список «До запуска» — пустые или тестовые
обязательные данные с учётом сохранённых контактов и адреса.

| Значение | Переменные | Почему не в админке |
|---|---|---|
| Бренд, официальное название | `NEXT_PUBLIC_BRAND_NAME`, `NEXT_PUBLIC_BUSINESS_NAME` | входят в фирменный стиль, иконки и метаданные, которые собираются при сборке |
| Город и его падежные формы | `config/business.ts` | используются в текстах и SEO-страницах; смена города — отдельная задача |
| Реквизиты продавца (ФИО/название, ИНН, ОГРНИП, юридический и фактический адрес, адрес возврата) | `NEXT_PUBLIC_SELLER_*` | юридически значимы (оферта, политика, чеки); меняются вместе с документами, а не из формы |
| Адрес сайта, этап (`preview`/`production`) | `NEXT_PUBLIC_SITE_URL`, `NEXT_PUBLIC_DEPLOYMENT_STAGE` | влияют на canonical, sitemap и индексацию |
| Режим каталога, показ остатков, б/у товары, рейтинги | `NEXT_PUBLIC_CATALOG_DATA_MODE`, `NEXT_PUBLIC_AVAILABILITY_DISPLAY_MODE`, `NEXT_PUBLIC_USED_PRODUCTS_ENABLED`, `NEXT_PUBLIC_RATINGS_ENABLED` | связаны с обменом с 1С и логикой каталога |
| Рассрочка, подтверждённые показатели, логотипы | `NEXT_PUBLIC_INSTALLMENT_ENABLED`, `NEXT_PUBLIC_CONFIRMED_*`, `NEXT_PUBLIC_LOGO_SOURCE` и др. | требуют подключения провайдера или подтверждения владельцем |

Переменные контактов, адреса, часов, доставки и услуг
(`NEXT_PUBLIC_CONTACT_PHONE`, `NEXT_PUBLIC_STORE_ADDRESS`,
`NEXT_PUBLIC_PICKUP_ENABLED` и т. д.) остаются **значениями по умолчанию**:
они действуют, пока настройки ни разу не сохранялись. После первого
сохранения сайт берёт эти данные только из базы, и изменение переменных на
них уже не влияет. Production-сборка по-прежнему проверяет, что телефон,
email и адрес заданы в окружении (`assertProductionBusinessConfig`).

## Хранение

Таблица `store_settings`, ключ `site_settings` (`SITE_SETTINGS_KEY` в
`lib/site-settings.ts`), значение — весь объект `SiteSettings` (JSONB),
описание строки — по-русски. Миграция не нужна: строка создаётся при первом
сохранении. Сохранение — одна транзакция: блокировка строки, проверка версии,
запись, запись в журнал.

Код:

- `lib/site-settings.ts` — тип, значения по умолчанию, адрес уведомлений
  (`getManagerNotificationEmail`);
- `server/services/site-settings-service.ts` — чтение (`getSiteSettings`,
  `readSiteSettings`) и сохранение (`SiteSettingsService.save`,
  `saveSiteSettings`);
- `server/repositories/site-settings-repository.ts` — SQL;
- `app/api/admin/settings/route.ts` — API;
- `components/admin/settings-section.tsx` (+ `settings-fields.tsx`,
  `settings-environment.tsx`) — раздел админки.

## Как изменения попадают на сайт

1. **Страницы.** Серверные страницы читают настройки через `getSiteSettings()`
   (один запрос к базе на запрос страницы). После успешного сохранения сервер
   сбрасывает кэш всех страниц (`revalidatePath("/", "layout")`,
   `revalidateWholeSite` в `server/cache/storefront-revalidation.ts`):
   следующий посетитель получает страницу с новыми данными. Если сброс не
   удался (ошибка записана в журнал сервера), сохранение всё равно проходит
   (`cacheReset: false` в ответе), а страницы обновятся по своему обычному
   интервалу.
2. **Заказы и заявки.** `OrderService` читает сохранённые настройки при
   каждом заказе: способ получения и шиномонтаж проверяются по текущим
   значениям (`422 DELIVERY_METHOD_UNAVAILABLE`, `422
   TIRE_SERVICE_UNAVAILABLE`), письмо сотрудникам о заказе ставится в очередь
   на текущий «email для обращений». `FitmentRequestService` так же берёт
   адрес для заявок на подбор. Это действует сразу, без кэша: покупатель с
   давно открытой формой получит понятный отказ, а не заказ с выключенным
   способом.
3. **Изменения в базе вручную** (SQL) кэш не сбрасывают: страницы обновятся
   по интервалу или после следующего сохранения в админке.

## Значения по умолчанию и сбои

- Нет `DATABASE_URL` (предпросмотр, демо Cloudflare) — сайт использует
  значения из сборки (`NEXT_PUBLIC_*`); API настроек отвечает `503
  SITE_SETTINGS_STORAGE_NOT_CONFIGURED`.
- Строки нет (настройки не сохранялись) — значения из сборки; в админке
  пометка «Настройки ещё не сохранялись».
- Строка повреждена (не проходит проверку) — значения из сборки целиком,
  предупреждение в журнале сервера (только пути полей), в админке —
  пометка; сохранение формы заменяет повреждённую строку.
- База временно недоступна — страницы показывают значения из сборки; заказ
  в это время всё равно не оформится (`503`).

Чтобы вернуться к значениям из окружения, удалите строку
(`DELETE FROM store_settings WHERE key = 'site_settings'`): заказы и заявки
сразу проверяются по значениям из сборки, страницы обновятся по своему
интервалу (как при любой ручной правке в базе).

## API

`GET /api/admin/settings` — `manager`, `admin`. Ответ (`Cache-Control:
no-store`):

```json
{ "ok": true, "settings": { … }, "updatedAt": "2026-10-12T08:00:00.000001Z",
  "defaults": false, "storedInvalid": false, "canEdit": true }
```

`updatedAt` — версия для следующего сохранения (`null`, пока строки нет);
`defaults` — значения взяты из сборки; `canEdit` — может ли текущий
сотрудник сохранять.

`PUT /api/admin/settings` — только `admin`, `Content-Type: application/json`
(иначе `415`), тело до 64 КБ (иначе `413`):

```json
{ "settings": { …весь объект SiteSettings… }, "expectedUpdatedAt": "2026-10-12T08:00:00.000001Z" }
```

Ответы: `200` (`changed`, `changedFields`, новый `updatedAt`, `cacheReset`);
`401` без входа; `403 ACCESS_DENIED` для менеджера и покупателя, `403
UNTRUSTED_ORIGIN` для запроса с другого сайта; `409
SITE_SETTINGS_VERSION_CONFLICT`; `422 VALIDATION_ERROR` с `details: [{ field:
"contacts.email", message }]` (путь поля, для списков — с номером строки,
например `contacts.additionalPhones.1`). Без изменений ничего не
записывается (`changed: false`).
