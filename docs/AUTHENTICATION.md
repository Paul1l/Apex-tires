# Регистрация и вход: покупатели и сотрудники

Два независимых способа входа:

- **покупатель** — email и код из письма (Yandex Cloud Postbox), сессия 30 дней;
- **сотрудник** (`manager`, `admin`) — страница `/admin`, email и 6-значный код
  из приложения-аутентификатора (TOTP), сессия 12 часов. Почта для входа
  сотрудников не нужна.

Права `manager` и `admin` действуют **только** в сессии, открытой входом
сотрудника. Если сотрудник войдёт на витрине по коду из письма, эта сессия —
покупательская: заказы и корзина работают, админка и её API — нет (страница
`/admin` покажет форму входа сотрудника, API ответит `403`).

## Вход покупателя: что реализовано

Покупатель регистрируется и входит без пароля:

1. вводит email;
2. сервер нормализует адрес и блокирует домены `gmail.com` и
   `googlemail.com`;
3. `POST /api/auth/request-code` создает 6-значный код и отправляет его через
   Yandex Cloud Postbox;
4. покупатель вводит код;
5. `POST /api/auth/verify-code` проверяет код, создает пользователя при
   регистрации и открывает серверную сессию;
6. браузер получает только `HttpOnly`, `SameSite=Lax`, `Secure` cookie и
   безопасный профиль пользователя.

Регистрация по номеру телефона в текущий релиз не входит. Поле `phone` в схеме
оставлено для будущего расширения.

## Текущий статус стенда

Код сценария и SQL-схема готовы, но реальная отправка на опубликованном стенде
не включена: нет production-БД, домена отправителя и ключей Postbox. В таком
состоянии API возвращает понятный `503`, не показывает фальшивое сообщение об
отправленном письме и не собирает персональные данные.

## Почему Yandex Cloud Postbox

Postbox предназначен для транзакционных писем и поддерживает API Amazon SES.
Первые 2 000 исходящих писем в календарный месяц не тарифицируются:

- https://yandex.cloud/ru/docs/postbox/pricing
- https://yandex.cloud/ru/docs/postbox/operations/send-email

Интеграция подписывает HTTP-запрос встроенным Web Crypto по AWS Signature
Version 4 и отправляет его на endpoint `https://postbox.cloud.yandex.net` с
регионом `ru-central1`. Внешний серверный SDK для этого не нужен.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `OTP_CODE_PEPPER` | секрет HMAC для кодов, контактов и сессий; без него в режиме database вход, сессии и гостевая корзина отвечают 503, а при старте сервера в журнале появляется `[config] ОШИБКА (OTP_CODE_PEPPER)` |
| `YANDEX_POSTBOX_ACCESS_KEY_ID` | ID статического ключа сервисного аккаунта |
| `YANDEX_POSTBOX_SECRET_ACCESS_KEY` | секретная часть статического ключа |
| `YANDEX_POSTBOX_FROM_EMAIL` | верифицированный адрес отправителя |
| `YANDEX_POSTBOX_FROM_NAME` | отображаемое имя отправителя |
| `DATABASE_URL` | PostgreSQL с примененными backend-миграциями |
| `OTP_MAX_FAILED_ATTEMPTS_PER_EMAIL` | неверных кодов на один email за скользящие 24 часа до блокировки (по умолчанию 15) |
| `RATE_LIMIT_AUTH_CODE_REQUESTS_PER_IP` | запросов кода с одного IP за час, включая ошибочные (по умолчанию 30) |
| `TRUSTED_PROXY` | источник IP клиента: `nginx`, `cloudflare` или `none` (см. `VDS_DEPLOYMENT.md`) |

`OTP_CODE_PEPPER` нужен и для входа сотрудников: ключи приложений-аутентификаторов
хранятся зашифрованными ключом, производным от него (см. «Смена OTP_CODE_PEPPER»).

Секреты нельзя добавлять в Git, клиентский JavaScript или обычные `vars`.
Их задают в менеджере секретов production-окружения.

## Подключение Postbox

1. Добавить в Postbox домен, с которого будут уходить письма.
2. Внести выданные сервисом DNS-записи и дождаться верификации.
3. Создать сервисный аккаунт в том же каталоге.
4. Выдать ему роль `postbox.sender`.
5. Создать статический ключ доступа.
6. Задать пять переменных `OTP_*` и `YANDEX_POSTBOX_*` из таблицы выше.
7. Отправить письмо на адрес симулятора Postbox, затем провести тест на
   реальных почтовых доменах.

## Защита сценария

- Код содержит ровно 6 цифр и живет 10 минут.
- В БД нет кода и email в открытом виде в таблице challenges: сохраняются
  HMAC-SHA-256 хеши.
- Один код можно использовать только один раз.
- После 5 неверных попыток требуется новый код.
- Общий лимит на адрес: после 15 неверных кодов за скользящие 24 часа (по
  всем кодам этого email) вход по адресу временно блокируется. Пока блокировка
  действует, новый код не отправляется, а введённый код не проверяется — даже
  верный. Блокировка снимается сама, когда старые ошибки выходят из 24-часового
  окна. Ответ — `429` с кодом `RATE_LIMIT_EXCEEDED` и сообщением о сроке, как у
  остальных лимитов OTP. Сброс вручную: удалить записи адреса из
  `otp_challenges` (адрес хранится только как HMAC).
- Повторная отправка доступна через 60 секунд.
- На один email допускается 3 запроса за 10 минут, на источник — 10.
- Дополнительно с одного IP принимается не больше 30 запросов кода в час,
  считая ошибочные (лимит в PostgreSQL, таблица `rate_limit_buckets`).
- `request-code` и `verify-code` принимают только запросы со страниц магазина
  (`Origin` сайта или `Sec-Fetch-Site: same-origin`) и только
  `Content-Type: application/json`. Это закрывает login-CSRF: чужая страница не
  может войти посетителем в свой аккаунт. Выход (`DELETE /api/auth/session`)
  проверяет `Origin` так же: чужая страница не может разлогинить посетителя
  (ответ `403 UNTRUSTED_ORIGIN`, сессия остаётся).
- Сессия покупателя живет 30 дней, токен в БД также хранится только как
  HMAC-хеш. В `sessions.auth_method` записано `customer_otp`: такая сессия не
  даёт прав сотрудника, даже если у учётной записи роль `manager` или `admin`.
- При регистрации отдельно фиксируются принятие правил и согласие на обработку
  персональных данных с версиями документов.

Блокировка по адресу защищает от подбора, но злоумышленник, знающий email,
может намеренно заблокировать вход владельцу на сутки. Перед публичным запуском
нужно добавить CAPTCHA после нескольких запросов (решение заказчика, нужен
внешний сервис), наблюдение за bounce/complaint событиями Postbox и регулярное
удаление просроченных `otp_challenges` и `sessions`. Персонал входит отдельно —
по коду из приложения-аутентификатора (ниже).

## Вход сотрудников (приложение-аутентификатор)

Сотрудник открывает `/admin`, вводит рабочий email и 6-значный код из
приложения: Google Authenticator, Яндекс Ключ, Microsoft Authenticator,
1Password и любое другое с поддержкой TOTP (RFC 6238). Код меняется каждые
30 секунд; часы телефона должны идти верно (автоматическое время).

Как устроено:

- код — TOTP по RFC 6238: HMAC-SHA1, шаг 30 секунд, 6 цифр, допускается
  отклонение часов на ±1 шаг; ключ 160 бит (`server/security/totp.ts`);
- ключ хранится в `staff_totp_credentials` только зашифрованным: AES-256-GCM,
  ключ шифрования выводится HKDF-SHA256 из `OTP_CODE_PEPPER` с отдельными солью и
  контекстом, формат `v1.<iv>.<данные>.<тег>`, идентификатор пользователя —
  связанные данные (ключ, скопированный в чужую строку, не расшифруется);
- один и тот же код дважды не принимается: сохраняется последний использованный
  30-секундный шаг, код этого или более раннего шага отклоняется;
- защита от подбора разделена на «доверенные устройства» и все остальные
  (подробно — в разделе «Доверенные устройства и блокировка» ниже): после
  **5 неверных кодов подряд** вход закрывается на **15 минут** — для
  доверенного устройства только на нём, для попыток без доверенного устройства —
  для всех новых устройств этой учётной записи; пока блокировка действует, не
  принимается даже верный код; каждая следующая ошибка снова закрывает вход на
  15 минут. Блокировки записываются в `admin_audit_log` (`staff.device_locked`,
  `staff.login_locked`);
- лимиты в PostgreSQL (`rate_limit_buckets`, ключи — HMAC), каждые 15 минут,
  считая удачные попытки: 20 попыток с одного IP (всегда); 10 попыток на
  введённый email — для попыток без доверенного устройства; 10 попыток на пару
  «email + доверенное устройство» — для попыток с ним;
- на неизвестный email, неверный или повторный код, заблокированную учётную
  запись, покупателя без прав и закрытый на время вход ответ один и тот же:
  `401 STAFF_LOGIN_FAILED` «Неверный email или код из приложения…» — по ответу
  нельзя узнать, чей это адрес;
- в журнал сервера пишется только причина отказа (`reason`) и признак
  доверенного устройства, без email, кода и токенов; удачный вход записывается
  в `admin_audit_log` (`staff.login`, с признаком `trustedDevice`);
- запрос принимается только со страницы магазина (`Origin`/`Sec-Fetch-Site`) и
  только как `application/json`;
- при успехе ставится та же cookie `apex_session` (`HttpOnly`, `SameSite=Lax`,
  `Secure` в production), сессия живёт **12 часов**, в `sessions.auth_method` —
  `staff_totp`. Выход — та же кнопка «Выйти» (`DELETE /api/auth/session`).

После применения миграции `010_staff_totp.sql` все существующие сессии считаются
покупательскими: сотрудники один раз входят в `/admin` заново по коду из
приложения.

Если PostgreSQL недоступен, `/admin` и остальные страницы `/admin/**` показывают
сообщение «База данных временно недоступна…» (страницы разделов переадресуют на
`/admin`), а API отвечает `503 DATABASE_UNAVAILABLE`.

### Доверенные устройства и блокировка

Защита от подбора устроена по схеме OWASP «device cookies» (миграция
`013_staff_trusted_devices.sql`). Цель — чтобы посторонний, знающий рабочий
email, не мог бесконечно держать сотрудника вне админки.

- После каждого успешного входа браузер получает cookie `apex_staff_device`:
  случайный токен 32 байта, `HttpOnly`, `SameSite=Strict`, `Secure` в
  production, срок **90 дней**, отправляется только на `/api/auth/staff/login`.
  В таблице `staff_trusted_devices` хранится лишь HMAC токена (с
  `OTP_CODE_PEPPER`, как у токенов сессий). При каждом входе токен меняется
  (скопированная старая cookie перестаёт действовать). Выход из админки
  cookie устройства не удаляет.
- Попытка с действующим токеном этой учётной записи («доверенное устройство»)
  считает ошибки только на этом устройстве: 5 неверных кодов подряд закрывают
  вход **с этого устройства** на 15 минут; блокировка учётной записи и лимит на
  email на неё не действуют, вместо лимита на email — лимит на пару «email +
  устройство».
- Попытка без действующего токена (новый браузер, очищенные cookie, чужой
  компьютер) считает ошибки на учётной записи: 5 неверных кодов подряд
  закрывают вход **со всех новых устройств** на 15 минут, действует лимит на
  email. Вход с доверенного устройства эту блокировку не снимает.
- Защита от повтора кода и лимит по IP действуют всегда; ответ при отказе
  один и тот же.
- Один браузер может быть доверенным для нескольких сотрудников (общий
  компьютер в магазине): cookie хранит до 5 токенов, каждый привязан к своей
  учётной записи. На учётную запись хранится до 10 устройств; давно не
  использованные и просроченные удаляются.
- Новый ключ, блокировка, смена роли и снятие прав удаляют все доверенные
  устройства сотрудника (вместе с его сессиями).

Остаточный риск: посторонний, знающий email, по-прежнему может закрыть вход с
**нового** устройства (первый вход на новом телефоне или после очистки cookie):
каждые 15 минут по 5 попыткам. Сотрудник при этом продолжает входить с уже
доверенных устройств. Если доверенных устройств нет (например, телефон потерян),
администратор выдаёт новый ключ в разделе «Сотрудники» (это также сбрасывает
блокировку), а для последнего администратора — команда создания администратора на сервере
(см. «Первый администратор»);
войти нужно сразу после этого. Дополнительная мера по решению владельца —
ограничить `/admin` и `/api/auth/staff/` списком IP-адресов магазина в nginx
(`allow …; deny all;`, как для обмена с 1С); по умолчанию не включено, потому
что сотрудники могут работать из разных сетей.

### Первый администратор

Первого администратора создают командой на сервере (открытой формы нет). Нужны
`DATABASE_URL` и **тот же** `OTP_CODE_PEPPER`, что у работающего сайта.

Локально:

```bash
DATABASE_URL=postgresql://… DATABASE_SSL_MODE=disable OTP_CODE_PEPPER=… \
  pnpm admin:create -- --email admin@example.ru --name "Имя Фамилия"
```

На VDS (Docker Compose, образ уже собран для `app`):

```bash
docker compose --env-file .env.production -f deploy/docker-compose.production.yml \
  --profile tools run --rm migrate \
  node_modules/.bin/tsx server/tools/create-staff.ts --email admin@example.ru --name "Имя Фамилия"
```

В образе нет `pnpm` (его скачивает corepack, а у сервиса `migrate` нет выхода в
интернет), поэтому на сервере команда вызывает `tsx` напрямую — это то же, что
`pnpm admin:create`. Сервис `migrate` получает `OTP_CODE_PEPPER` и
`NEXT_PUBLIC_BRAND_NAME` из `.env.production`.

Параметры: `--email` (обязательно), `--name` (обязательно для новой учётной
записи), `--role admin|manager` (по умолчанию `admin`). Если учётная запись с
таким email уже есть (например, покупатель), она получает роль, становится
активной, получает новый ключ, а все её сессии завершаются.

Команда печатает QR-код в терминале, ключ для ручного ввода и ссылку
`otpauth://`. **Это секрет:** не сохраняйте вывод в файлы, журналы и чаты,
очистите экран после подключения приложения. В приложении: «Добавить» →
«Сканировать QR-код» (или «Ввести ключ», тип — по времени), затем войти в
`/admin` с email и кодом.

### Сотрудники в админке

Раздел «Сотрудники» доступен только администратору (менеджер видит сообщение,
API отвечает `403`):

- **Добавить** — email, имя, роль. Если покупатель с таким email уже
  зарегистрирован, его учётная запись получает роль. Сразу показывается окно с
  QR-кодом и ключом; **ключ показывается один раз**, повторно его не увидеть —
  только выпустить новый. Ответ API с ключом не кэшируется (`no-store`).
- **Роль** — менеджер (каталог, заказы) или администратор (ещё и сотрудники,
  массовые операции).
- **Заблокировать / Разблокировать** — заблокированный не может войти.
- **Снять права** — учётная запись остаётся покупательской, ключ удаляется.
- **Новый ключ** — старый ключ перестаёт работать.

Смена роли, блокировка, снятие прав и новый ключ сразу завершают все сессии
этого человека и удаляют его доверенные устройства. Нельзя менять собственную роль и статус, нельзя снять права или
заблокировать последнего активного администратора. Каждое изменение пишется в
`admin_audit_log` (`staff.created`, `staff.promoted`, `staff.updated`,
`staff.revoked`, `staff.key_reissued`, `staff.provisioned_by_command`) без ключей
и кодов.

### Потерян или сменился телефон

1. Другой администратор открывает «Сотрудники» → «Новый ключ» у этого
   сотрудника и передаёт ему QR-код лично. Старый ключ и все сессии
   сотрудника перестают действовать.
2. Если телефон потерял **последний** администратор (войти в админку некому),
   на сервере выполняется команда создания администратора с `--email <его email>`
   (на VDS — через `tsx`, см. выше): учётная запись становится активной администраторской, получает новый
   ключ, блокировка входа снимается, доверенные устройства удаляются.

Если сотрудник просто сменил телефон и ещё может войти, администратор может
выпустить новый ключ и себе — после этого текущая сессия завершится, войти
нужно будет с кодом из нового ключа.

### Смена OTP_CODE_PEPPER

`OTP_CODE_PEPPER` — источник ключа шифрования ключей сотрудников. После его
смены сохранённые ключи не расшифровываются: **все сотрудники должны получить
новые ключи**. Порядок: задать новый `OTP_CODE_PEPPER`, перезапустить `app`,
выполнить команду создания администратора (на VDS — через `tsx`, см. выше) с
`--email <администратор>` и новым значением, войти
и выпустить новые ключи остальным в разделе «Сотрудники». Попытка входа со
старым ключом отклоняется, в журнале сервера появляется ошибка
«Staff authenticator key cannot be decrypted». Смена pepper также завершает все
сессии, отменяет доверенные устройства и сбрасывает лимиты (всё это хранится как
HMAC с этим секретом).

## Основные функции

| Функция | Назначение |
| --- | --- |
| `normalizeEmailAddress` | нормализует email и применяет запрет Gmail |
| `createSecureDigest` | вычисляет HMAC-SHA-256 для чувствительных значений |
| `generateSixDigitCode` | создает криптографически случайный OTP |
| `deliverAuthenticationCode` | отправляет письмо через Postbox |
| `POST /api/auth/request-code` | rate limit, создание challenge и отправка |
| `POST /api/auth/verify-code` | проверка OTP, аккаунт, согласия и сессия |
| `GET /api/auth/session` | восстанавливает профиль по серверной сессии (роль — с учётом способа входа) |
| `DELETE /api/auth/session` | отзывает текущую сессию |
| `POST /api/auth/staff/login` | вход сотрудника: email и код из приложения, сессия 12 ч, cookie доверенного устройства |
| `GET/POST /api/admin/staff` | список сотрудников; добавление с выдачей ключа (только `admin`) |
| `PATCH /api/admin/staff/{userId}` | роль (`manager`, `admin`, `customer` — снять права) и статус |
| `POST /api/admin/staff/{userId}/totp` | новый ключ, завершение сессий |
| `pnpm admin:create` | первый администратор и восстановление доступа на сервере |
| `verifyTotp`, `buildOtpauthUri` | проверка кода RFC 6238 и ссылка для приложения |
| `encryptStaffSecret` / `decryptStaffSecret` | шифрование ключей сотрудников |
| `getStaffPageAccess` / `requireUserRole` | доступ страниц `/admin/**` и API; одинаковое правило ролей |

## PostgreSQL и роли

OTP, пользователи и сессии обслуживаются слоями `AuthService` и
`AuthRepository` в PostgreSQL; вход и управление сотрудниками — `StaffAuthService`,
`StaffManagementService` и `StaffRepository` (миграции `010_staff_totp.sql` и
`013_staff_trusted_devices.sql`).
Старый D1-адаптер удалён. Роли `customer`, `manager` и `admin` проверяются
сервером; cookie или поля frontend не могут повысить права. Роль сессии
вычисляется из роли учётной записи и способа входа (`sessions.auth_method`):
`manager`/`admin` — только для `staff_totp`. `/admin`, импорт, административные
заказы и изменение статуса закрыты server-side проверкой. Первого
администратора создают командой `pnpm admin:create` на сервере (см. выше), а не
SQL-операцией и не открытой формой.

Публичный preview по-прежнему возвращает `503`, потому что на нём намеренно нет
production PostgreSQL и ключей Postbox.
