# Регистрация и вход по email

## Что реализовано

Покупатель регистрируется и входит без пароля:

1. вводит email;
2. сервер нормализует адрес и блокирует домены `gmail.com` и
   `googlemail.com`;
3. `POST /api/auth/request-code` создает 6-значный код и отправляет его через
   Yandex Cloud Postbox;
4. покупатель вводит код;
5. `POST /api/auth/verify-code` проверяет код, создает пользователя при
   регистрации и открывает серверную сессию;
6. браузер получает только `HttpOnly`, `SameSite=Lax`, `Secure` cookie и
   безопасный профиль пользователя.

Регистрация по номеру телефона в текущий релиз не входит. Поле `phone` в схеме
оставлено для будущего расширения.

## Текущий статус стенда

Код сценария и SQL-схема готовы, но реальная отправка на опубликованном стенде
не включена: нет production-БД, домена отправителя и ключей Postbox. В таком
состоянии API возвращает понятный `503`, не показывает фальшивое сообщение об
отправленном письме и не собирает персональные данные.

## Почему Yandex Cloud Postbox

Postbox предназначен для транзакционных писем и поддерживает API Amazon SES.
Первые 2 000 исходящих писем в календарный месяц не тарифицируются:

- https://yandex.cloud/ru/docs/postbox/pricing
- https://yandex.cloud/ru/docs/postbox/operations/send-email

Интеграция подписывает HTTP-запрос встроенным Web Crypto по AWS Signature
Version 4 и отправляет его на endpoint `https://postbox.cloud.yandex.net` с
регионом `ru-central1`. Внешний серверный SDK для этого не нужен.

## Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `OTP_CODE_PEPPER` | секрет HMAC для кодов, контактов и сессий |
| `YANDEX_POSTBOX_ACCESS_KEY_ID` | ID статического ключа сервисного аккаунта |
| `YANDEX_POSTBOX_SECRET_ACCESS_KEY` | секретная часть статического ключа |
| `YANDEX_POSTBOX_FROM_EMAIL` | верифицированный адрес отправителя |
| `YANDEX_POSTBOX_FROM_NAME` | отображаемое имя отправителя |
| `DB` | серверная БД с примененной `database/schema.sql` |

Секреты нельзя добавлять в Git, клиентский JavaScript или обычные `vars`.
Их задают в менеджере секретов production-окружения.

## Подключение Postbox

1. Добавить в Postbox домен, с которого будут уходить письма.
2. Внести выданные сервисом DNS-записи и дождаться верификации.
3. Создать сервисный аккаунт в том же каталоге.
4. Выдать ему роль `postbox.sender`.
5. Создать статический ключ доступа.
6. Задать пять переменных `OTP_*` и `YANDEX_POSTBOX_*` из таблицы выше.
7. Отправить письмо на адрес симулятора Postbox, затем провести тест на
   реальных почтовых доменах.

## Защита сценария

- Код содержит ровно 6 цифр и живет 10 минут.
- В БД нет кода и email в открытом виде в таблице challenges: сохраняются
  HMAC-SHA-256 хеши.
- Один код можно использовать только один раз.
- После 5 неверных попыток требуется новый код.
- Повторная отправка доступна через 60 секунд.
- На один email допускается 3 запроса за 10 минут, на источник — 10.
- Сессия живет 30 дней, токен в БД также хранится только как HMAC-хеш.
- При регистрации отдельно фиксируются принятие правил и согласие на обработку
  персональных данных с версиями документов.

Перед публичным запуском нужно добавить CAPTCHA после нескольких запросов,
наблюдение за bounce/complaint событиями Postbox и регулярное удаление
просроченных `otp_challenges` и `sessions`.

## Основные функции

| Функция | Назначение |
| --- | --- |
| `normalizeEmailAddress` | нормализует email и применяет запрет Gmail |
| `createSecureDigest` | вычисляет HMAC-SHA-256 для чувствительных значений |
| `generateSixDigitCode` | создает криптографически случайный OTP |
| `deliverAuthenticationCode` | отправляет письмо через Postbox |
| `POST /api/auth/request-code` | rate limit, создание challenge и отправка |
| `POST /api/auth/verify-code` | проверка OTP, аккаунт, согласия и сессия |
| `GET /api/auth/session` | восстанавливает профиль по серверной сессии |
| `DELETE /api/auth/session` | отзывает текущую сессию |

## База для реального запуска в РФ

Текущий интерфейс хранилища написан под D1, чтобы проверить API-контракт на
закрытом стенде. Для реальных аккаунтов первичная база персональных данных
должна быть заменена на PostgreSQL и backend, физически размещенные в РФ.
Cloudflare D1 не следует использовать как первичное место хранения
персональных данных российских покупателей. Детали миграции перечислены в
`docs/DATABASE.md`.
