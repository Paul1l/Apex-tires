# LocalFitmentProvider

`FitmentProvider` описывает listMakes/listModels/listGenerations/
listModifications/getFitments. Текущий адаптер читает PostgreSQL; браузер
обращается к API справочников и каталога. OpenAI в этой цепочке не используется.

Справочники отдаются по выбранному родителю, не всей таблицей применяемости.
В подбор входят только verified=true. Последовательность: марка → модель →
поколение → технические fitments → индексированный SQL → страница товаров.
Классический UI выбирает поколение. Dropdown модификаций появляется, если в базе
есть такие записи, и требует явного выбора. Без модификации SQL использует только
общие записи поколения. Различия передней/задней оси сохраняются в данных;
отдельный UX покупки разноширокого комплекта требует проверки на реальном ассортименте.

Шины совпадают по width/profile/diameter. Диски — diameter/width/bolt_count/pcd,
ET внутри заданного диапазона, DIA не меньше требуемого. Больший DIA может
требовать центровочного кольца: совпадение фильтра не обещает установку без
дополнительных деталей. Применяемость не генерируется LLM.

`GET /api/v1/fitments/products` возвращает items/pagination/facets/fitments,
а не тысячи productIds. Требуется generation. Основной каталог принимает
vehicleMake/vehicleModel/vehicleGeneration/vehicleModification и делает тот же
SQL EXISTS. Размер выдачи ограничен 24/48/96.

Не найденный автомобиль: форма сохраняет vehicle_fitment_requests.
Раздел «Заявки на подбор» показывает по 50 заявок; manager/admin может менять
new/in_progress/resolved/closed, действие попадает в аудит.

Старая product_fitments оставлена только для совместимости протокола 1С.
Она не является источником нового нормализованного подбора: будущему адаптеру
1С нужно согласованно заполнять car_* и fitments.
