# Реестр задач и решений: аудит, дизайн, изображения шин

Запрос заказчика (10.10.2026): провести аудит сайта, предложить более
узнаваемый дизайн, создать изображения для каждого наименования шины.

Исходное состояние: ветка `claude/magical-cray-rc1s4m` = `main` (`ab725a7`);
`lint`, `typecheck`, 28/28 тестов — без ошибок.

## Решения

| ID | Решение | Причина |
|---|---|---|
| D1 | Дизайн выдаётся как предложение: спецификация + статический прототип в `docs/design-proposal/`. Код витрины под новый дизайн не переводится до согласования. | В запросе «предложить»; на прошлом этапе дизайн сознательно не менялся. |
| D2 | Изображения шин — детерминированные SVG-иллюстрации, генерируемые из атрибутов товара (бренд, модель, сезон, шипы, размер). Показываются, только если у товара нет фото; фото из 1С/CSV имеет приоритет. Помечаются как иллюстрация. | Генератора фотографий в среде нет; выдавать рисунок за фото товара нельзя; решение должно работать и для товаров из PostgreSQL. |
| D3 | Аудиторы работают только на чтение. Исправления вносят владельцы файлов после разбора; в этой итерации — Critical/High и недорогие Medium. | Независимость проверки, отсутствие конфликтов в файлах. |
| D4 | Изображения дисков вне объёма задачи. | В запросе только шины. |
| D5 | Новые npm-зависимости не добавляются. Playwright/Chromium берутся из среды для проверок. | Без изменения стека. |
| D10 | 500 на битом %-кодировании пути (`/tires/%E0%A4%A`) не исправляется в приложении: ошибка в роутере Next.js до нашего кода; правило nginx от T8d проверено только регуляркой — оставлено рекомендацией до проверки на staging. | Непроверенный конфиг nginx может остановить сайт; эффект — только шум в логах. |
| D11 | Сообщение о нехватке остатка показывает точное количество только в режиме показа `exact`; в остальных режимах — без числа. | Не раскрывать остатки, которые владелец решил скрывать. |
| D12 | Trivial-дефекты QA-11, QA-16, QA-19, QA-20 не исправляются в этой итерации и перечислены в `SITE_AUDIT.md` как известные. | Не обязательны по критериям готовности; каждый круг исправлений требует новой независимой проверки. |
| D13 | Концепция дизайна «Катунь» (T4) отклонена заказчиком: «сильно ИИшный». Новое направление — строгий функциональный каталог, без фотографий. Файлы v1 удалены из рабочей версии, остаются в истории (commit 66e1d6b). | Решение заказчика. |
| D14 | Дизайн на паузе по решению заказчика; в волне T13 внешний вид витрины не меняется. Оставшиеся пункты аудита и QA без решений владельца выполняются. QA-14, CAPTCHA, срок резерва, письма, роли, SEC-10, SEC-13, SEC-16, SEO-11, PERF-05, UX-07 — ждут решений владельца или дизайна. | Решение заказчика «пока с дизайном стоп, остальное делай». |
| D15 | `sharp` 0.35.5 и `source-map-js` 1.2.2 обновлены в пределах диапазонов (commit 9e1ffa3); `pnpm audit --prod` — 0 уязвимостей. | Закрыть остаточные advisory. |
| D16 | Заказчик решил оставить текущий (исходный) дизайн сайта. Предложения v1 и v2 удалены из рабочей версии, остаются в истории (66e1d6b, 8f8f64e). Исправления доступности в рамках текущего стиля сохраняются. | Решение заказчика «оставь изначальный дизайн и продолжай работу». |
| D6 | Из находок T1 в рекомендации (не исправляем сейчас): CAPTCHA (нужны внешний сервис и ключи), срок резерва и письма на неподтверждённый email (решение владельца), SEC-09/10/11/13/15/16. | Внешние сервисы и бизнес-правила — решение заказчика; Low — вне D3. |
| D7 | Одновременно работают 4 исполнителя (T4, T5a, T5c, T5d): наборы файлов не пересекаются, ресурсов достаточно (4 CPU, 14 ГБ RAM). | Исключение из лимита 3 по правилу «независимые задачи и достаточные ресурсы». |
| D8 | Падежные формы города (`cityPrepositional`, `cityDative`) добавлены руководителем в `config/business.ts` до старта T5c/T5d — общий контракт. | Один владелец общего конфига. |
| D9 | Иллюстрации шин остаются data URI в `<img>`: 8 SVG ≈ 13 КБ в gzip, при серверном рендеринге 24 карточек ≈ 40 КБ gzip. | Отдельный маршрут изображений пока не оправдан. |
| D17 | Админка — основное место управления каталогом (товары, цены, остатки, фото, применимость), заказами и настройками сайта. Сотрудники входят по email и коду из приложения-аутентификатора (TOTP, RFC 6238), без Postbox; первый администратор — командой на сервере, остальные — в разделе «Сотрудники». | Решения заказчика 11.10.2026: «В админке сайта», «Приложение-аутентификатор». |
| D18 | Добавлена зависимость `qrcode-generator` 2.0.4 (MIT, без зависимостей, выпуск 08.2025): QR-код для подключения приложения-аутентификатора в админке и в консоли. `pnpm audit --prod` — 0 уязвимостей. Свой генератор QR — лишний риск ошибок. | Обоснование руководителя по правилу о зависимостях. |
| D19 | Волна T21: 3 исполнителя параллельно, наборы файлов не пересекаются. Общий контракт — `server/security/staff-page-guard.ts` (`getStaffPageAccess`) для страниц `/admin/**` и `requireUserRole` для API; оба меняет только T21a. Миграции: 010 — T21a, 011 — T21b, 012 — T21c. Стили новых экранов — CSS-модули рядом с компонентами, `app/globals.css`, `lib/types.ts`, `server/bootstrap/application-services.ts`, `components/admin-dashboard.tsx` не меняются исполнителями. Сборку (`next build`) запускает только руководитель при приёмке в отдельной копии. | Исключить конфликты правок и гонки сборки. |
| D20 | Письма покупателю о смене статуса заказа подготовлены (текст и постановка в очередь), но выключены флагом до решения владельца: нужен шаблон в провайдере Postbox и согласие владельца на такие письма. Отметку оплаты меняет только `admin`; менеджеру смена оплаты теперь запрещена (раньше была доступна через запрос смены статуса). | Внешние рассылки — только с разрешения заказчика; роли — решение владельца. |
| D21 | QA-28: блокировка входа сотрудника чужими попытками снимается «доверенными устройствами» (рекомендация OWASP): после успешного входа браузер получает отдельную cookie на 90 дней; попытки с ней считаются по устройству, а общая блокировка учётной записи и лимит по email действуют только на попытки без неё. Ограничение `/admin` по IP в nginx — по желанию владельца. Перекодирование фото (sharp) не вводим: тип по содержимому, структурная проверка, `nosniff`, фиксированный `Content-Type` и CSP `sandbox` достаточно. | Баланс защиты от перебора и от блокировки чужими руками; без новых зависимостей. |
| D22 | Одновременно 4 исполнителя (T23b, T24a, T24b, T24c): небольшие исправления в непересекающихся файлах, сборку запускает только руководитель. | Исключение из лимита 3 по правилу «независимые задачи и достаточные ресурсы» (как D7). |
| D23 | Письма покупателю о смене статуса: заказчик ответил «присылать». Включение заблокировано средой как внешнее действие — ждёт явного разрешения заказчика в среде; код письма готов (T21c), флаг выключен. | Внешние рассылки — только с подтверждённого разрешения. |
| D24 | По вопросам T23b: (1) при сбое базы `getSiteSettings` оставляет значения сборки — ISR-страница может до 5 минут показывать контакты из окружения; бросать ошибку нельзя: корневой layout общий с админкой и документами (вернулись бы 500, QA-34). (2) Проверка production-сборки по-прежнему требует телефон, email и адрес в окружении — это запасные значения на случай сбоя базы. (3) Дополнительные телефоны, балансировка, установка, хранение, другие услуги и ВК сохраняются, но на витрине не показываются — показ меняет дизайн (D16), решение заказчика. | Безопасная деградация и неизменный дизайн. |
| D25 | `.next` в образе принадлежит пользователю приложения (`COPY --chown`), как в официальном примере Next.js: ISR сохраняет обновлённые страницы на диск, после перезапуска не отдаётся HTML времени сборки. Риск «приложение может изменить свой собранный код» принят: при выполнении кода в процессе приложения у него и так есть доступ к базе. | Корректная работа ISR и настроек сайта после перезапуска. |
